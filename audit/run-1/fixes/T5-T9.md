## C-2: deleted campaign's bank adopted by a same-named new campaign

Cause: two. `remove` only filtered the campaign list, and the id was `slug(name)`, so a reused name reused the id and its bank.

Change:
- `bank.ts`: `removeCampaignBank` and `bankStore.removeCampaign`. `CampaignContext.remove` calls it.
- `campaigns.ts`: `newCampaignId()` gives opaque ids (`c-<16 hex>`), no longer derived from the name. `createCampaign` takes an injectable id maker and skips ids already taken.

Migration: ids are opaque strings everywhere, so existing slug ids (`acme-q4`) keep working with no rewrite. Existing campaigns and banks are untouched. Only newly created campaigns get the new id shape. Orphaned banks already in a user's settings.json (from past deletes) are left in place, not auto-pruned: pruning at load could wipe real banks if a campaign entry failed to parse. They cannot be adopted any more, since no new id equals an old slug key (the case where the user still has a campaign with that slug is just that campaign). A one-off cleanup of old orphans is a product decision I did not make.

Tests: `src/context/CampaignContext.test.ts` renders the real `CampaignProvider` over a settings.json in today's shape (slug ids, two banks, used ranges). It proves both campaigns, banks and the active id load intact, then that removing one deletes its bank (in memory and in the persisted value) and leaves the other, and that recreating "Acme Q4" gets a different id and starts empty. Also `campaigns.test.ts` (opaque ids, stored slugs load and update unchanged) and `bank.test.ts` (`removeCampaignBank`). Two older tests that asserted slug ids were updated.

Note: a control that makes the id constant also loops forever in `uniqueId` against my collision test. That is a property of the broken variant, not of the shipped code.
