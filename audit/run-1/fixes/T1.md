## Cancel contract (G-10) — for the coordinator to confirm against T4

- Route: `POST /api/download/cancel`
- Body: `{ "jobId": "<id>" }` (JSON). `?jobId=<id>` in the query is also accepted.
- Missing jobId: `400 {"error":"jobId is required"}`.
- Response: `200 {"ok":true,"found":boolean}`. `found:true` means a job with that
  id was still being built and has been cancelled; `found:false` means unknown or
  already finished/failed. Both are 200 and harmless; a late cancel never removes a
  finished clip (tested).
- Effect: every yt-dlp and ffmpeg child of that job is killed with its process
  group (`taskkill /T /F` on Windows), the job stops before starting another step.
  The cancelled `/api/download` request itself answers `499
  {"error":"Cancelled","code":"cancelled","cancelled":true}`; its progress channel
  publishes `phase:"error", message:"Cancelled"`. Resumable `.part` data is kept;
  the job's own clip folder is removed.
- Hanging up the download request (AbortController) cancels it the same way, so
  T4's abort + POST is consistent; the POST is the reliable half.
- Jobs are registered per request, so two jobs with the same jobId or the same clip
  are independent; cancelling one does not touch the other (tested: A cancelled, B's
  yt-dlp stays alive and B returns 200 with its clip on disk).
- Renderer note: it must treat status 499 / `code:"cancelled"` as "user cancelled",
  not as a failure to report or diagnose.

## Per finding

### G-1 (blocker) — shared work folder
Cause: the folder was keyed on `[url, format, quality, ranges]` only, and each
start did `rmSync` on the output, list and segment paths. Two requests with the
same key therefore shared `clip.mp4`, and each one's cleanup deleted the other's.
Change: two folders. The keyed folder is still used for what must survive a failure
(`.part`, whole-file `source.*`, segment files) so retry/resume still works, but a
live job holds an exclusive claim on it (`tryClaim`); a second identical job works in
a private folder instead. The clip, concat list and join output always go in a
per-request folder `ytclip-<hash>-<random>` (`jobDir`). The prefix is unchanged, so
the main process's `ytclip-` save check and its removal of the clip's directory still
work. Test: two identical concurrent downloads get different paths, both files
exist, and each reported size equals the file at its path.

### G-2 — loopback bind and origin
Cause: `app.listen(PORT)` bound 0.0.0.0 and `cors()` allowed `*`.
Change: `listen(PORT, "127.0.0.1")`. Requests carrying an Origin other than
`http://127.0.0.1|localhost:<PORT>` or the dev renderer
(`:8080`) get 403 BEFORE any route runs (CORS headers alone would not stop the
no-preflight `text/plain` POST, which the browser sends and Express would process).
A Host that is not `127.0.0.1`, `localhost` or `[::1]` is also 403 (DNS rebinding).
Requests with no Origin (Electron main process, curl, same-origin GET) pass.
Tests: foreign-origin `text/plain` POST to `/api/cache/clear` is 403 and the
folder survives; preflight 403 with no allow-origin; `/api/info` from a foreign
origin never starts yt-dlp; the own origin and `localhost:8080` still get 200/204
with the matching allow-origin; rebinding Host 403; connecting to a non-loopback
interface address is refused (skipped silently if the machine has none).
Risk to watch: the Electron renderer loads from `http://127.0.0.1:<port>` (checked
in `electron/main.cjs`), which is allowed. I did not launch Electron for this.
Anything that reaches the server by another hostname will now get 403.

### G-3 — URL check
Cause: substring regex over the whole string. Change: `isYouTubeUrl` parses the
URL, requires http/https, no userinfo, and host `youtube.com`, `*.youtube.com` or
`youtu.be`. Test: nine bad URLs (userinfo, path/query/fragment containing
youtube.com, link-local, loopback, `file:`, `youtube.com.evil.example`,
`notyoutube.com`, `ftp:`) all 400 and yt-dlp is never run; five real hosts pass.
`channelRoutes.ts` shares `urlSchema`, so it gets the fix too.

### G-4 / G-6 — pre-roll leak and silent wrong length
Cause (G-4): `-ss` before `-i` with `-c copy` keeps packets back to the previous
keyframe behind an mp4 edit list; the concat demuxer ignores it.
Change: the local trim now decodes and re-encodes from the exact in-point
(`localTrimArgs`: libx264 crf 18 veryfast, yuv420p, aac 192k, `-fps_mode
passthrough`, length by `-t`). Pre-roll is discarded, not hidden. Audio-only
trimming already re-encoded and is unchanged. Cost: the whole-file fallback path
now spends CPU time re-encoding the cut instead of copying; it is only reached when
the sectioned download 403s. The sectioned path (`--force-keyframes-at-cuts`) is
untouched and still not provable here.
Cause (G-6): `durationOk` was logged and dropped. Change: a join that fails the
server's own length check now fails the job (`join_failed`, with the measured and
expected lengths, diagnostics attached), deletes the bad file, and returns no path.
Tests: G-4 runs the real server and real ffmpeg on `[0.5–2.25] + [10.1–12.35]`
and identifies every delivered frame against all 750 source frames (nearest
thumbnail; a stream-copied frame matches itself at distance 0).
G-6 sends three 5 s marks through a fake that writes the whole 30 s file per piece
(about 90 s joined) and asserts a non-200 `join_failed` with no clip left on disk.

Measured, G-4 end to end through the server (copy join, `joinMethod:"copy"`):

| | before fix | after fix |
|---|---|---|
| marked | 4.00 s / 100 frames | 4.00 s / 100 frames |
| delivered frames | 115 (114 decoded) | 99 |
| frames from before an in-point | 14 | 0 |
| frames after an out-point | 0 | 0 |
| first delivered source frame | 0.04 s (in-point 0.50) | 0.52 s |
| last delivered source frame | 12.32 s | 12.32 s |
| joined duration | 4.54 s | 4.00 s |
| worst decoded-frame distance to its source frame | 0 (copy) | 0.10 (re-encode) |

One frame short of the 100 marked: the in-point 0.50 s is not on the 25 fps grid
(first frame 0.52) and `-t` stops before a frame that starts at 2.24 s but ends past
2.25 s. This is the sub-frame rounding of the marks, never extra footage. A
decoded-frame CHECKSUM comparison to the source is only possible for a stream copy;
a re-encoded frame cannot be bit-identical, so identity is by nearest-frame match
with a margin (min gap to the runner-up 0.29 vs worst distance 0.10 on this
fixture) rather than md5.

### G-5 — cookie jar
Cause: four routes called `resolveCookieOptions()` and passed the canonical path.
Change: info, transcript, comments and sign-in status run through `withRunCookies`
(private copy, discarded on release; one copy covers the three-probe loop). Only
download segment one may promote a jar. `cookieJar.ts` itself needed no change.
Test: with a jar and a fake that overwrites its `--cookies` file with an empty file
on exit, all four routes run with a private path and the canonical jar is
byte-identical afterwards. `channelRoutes.ts` still calls `resolveCookieOptions`
directly (T7's file; see below).

### G-8 — Clear cache deleting live work
Cause: no in-use registry. Change: `resumeCache.ts` gains `markInUse`, `tryClaim`,
`holdFolder`, `releaseHold`, `isProtected`; `clearCache()` and the stale sweep skip
protected folders and `clearCache` returns `{removed, skipped}`. The clip route marks
both its folders for the life of the job and, after a `deliver:"path"` 200, HOLDS the
clip folder for 30 minutes (`HANDOFF_HOLD_MS`) because its only copy sits there until
the main process moves it. `/api/cache/clear` returns `skipped` too.
Test: multi-segment job running (the join_failed scenario from the audit) while Clear
cache is called: an abandoned folder is removed, the job still finishes with 200 and
the finished clip survives a second Clear. Plus unit tests of the registry.
Not fixed here (renderer): the "Clear partials" label still sits on a button whose
endpoint earlier deleted finished clips; now finished uncollected clips are safe for
30 min, but that wording belongs to the Downloads panel owner.

### G-9 — damaged cached download
Cause: `findDownloaded()` accepted any `source.*`, `pruneWorkDir` keeps it on
failure, and the error shown was ffmpeg's banner (no `-hide_banner`).
Change: a source is used only if ffmpeg reports a duration; a cached one that is not
readable is deleted and re-fetched; a fresh one that is still unreadable is deleted
and the job fails with "The downloaded video file is damaged and was discarded…".
Trim commands now pass `-hide_banner`. Tests: (1) a damaged download fails with a
message that says "damaged" and has no ffmpeg banner, and the next attempt succeeds;
(2) a truncated `source.mp4` planted in the shared folder is discarded and re-fetched.

### G-10 — see contract above
Cause: nothing kept a child handle and nothing listened for the hang-up. Children are
tracked per job, started in their own process group, and killed on cancel or hang-up;
the auth-probe loop no longer starts the next probe target after the client left.
Tests: cancel route kills A within 3 s (yt-dlp would sleep 8 s) while identical B
survives and finishes; hang-up kills yt-dlp; unknown/finished/missing id.
Not covered: killing an ffmpeg join in flight (`runProcess` lives in `segments.ts`,
not mine); the job stops before and after it.

### E-7 — CSV formula injection
Change: `csvCell` prefixes a string beginning `= + - @ \t \r \n` with `'`, still fully
quoted RFC 4180. Numbers and plain-number strings (e.g. `-5`) are left alone. A test
round-trips fields with comma, quote, CRLF, emoji and a leading `=` through an RFC 4180
reader.

### F-5 — diagnostics on pre-flight failures
Cause: the pre-flight paths used `sendFailure` without `diagnostics`. Change: the job
id is now derived first; every pre-flight failure (probe error, cookie error, out
point past end, 401 no-session, stale-session, 429) carries `diagnostics`. Test:
probe failure returns `diagnostics.jobId` and the stderr; out-point failure carries it.
