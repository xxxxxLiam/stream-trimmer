## D-2 clip:save overwrote an existing clip
Cause: `fsp.rename(source, target)` replaces silently. Change: `moveWithoutOverwrite`
(`pathSafety.cjs`) hard-links source to the target, which fails with EEXIST instead of replacing,
and retries ` 2`, ` 3` (same convention as `uniquePath` in `editorOpen.cjs`); falls back to an exclusive
copy (`COPYFILE_EXCL`) where links are unavailable (other device, exFAT). That is race-safe, unlike an
`existsSync` check. `file:save` (the fallback clip path and the comments CSV) now writes with flag `wx`
and the same numbering, since it destroyed files the same way.
Real app, before: original `ino=1057185 size=120 sha=af92b8166acf` -> after `ino=1057250 size=14
sha=ebd5783df34f`, dir listing `[clip.mp4]`. After the fix: ino/size/sha unchanged
(`ino=1089944 size=120 sha=af92b8166acf`), new clip saved as `clip 2.mp4`, result path points at it.
Tests: `pathSafety.test.ts` (inode+size+sha of the original, ` 2`, ` 3`, free name, `wx` write).

## F-6 diagnostics:copy put the raw log on the clipboard
Cause: `clipboard.writeText(logger.tail(500))`. Change: main now writes
`redact(tail, { homeDir: os.homedir() })`. `src/lib/diagnostics.ts` is T8's and is TS, so the rules are
duplicated in `electron/redact.cjs`; `redact.test.ts` asserts byte-identical output to the renderer's
`redact()` on the planted log (drift guard) and that no marker survives.
Real app, actual clipboard string, 9 planted synthetic markers: before 9/9 leaked (shapes
`SYNTHsidv…`, `SYNTHbear…`, `SYNTHacce…`, `SYNTHsig…`, `someone.s…`, `/root/…`, `SYNTHcook…`,
`yt-cookie…`, `SYNTHpo…`); after 0/9, harmless lines intact (`access_token=<redacted>`,
`sig=REDACTED`, `<email>`, `~/clips/...`, `Cookie: <redacted>`, `--cookies <redacted>`).

## G-12 BOM settings.json destroyed; no backup
Cause: `readFile()` swallowed every parse error as `{}`, and the next `persist()` renamed that over the
original. Change (`settingsStore.cjs`): `parseSettingsText` strips a BOM and trims; an unparseable file
(bad JSON, array, trailing junk) is copied byte-for-byte to `settings.json.corrupt-<sha256 prefix>`
first (idempotent per content, logged once through the main log), and `persist()` refuses to write if
neither a parse nor a backup succeeded. Blank/missing files need no backup.
Real app, BOM + 3-row bank, after boot and after a user write: before `keys=1 bank=0` (data gone), after
`keys=7/8 bank=3`. Unparseable file: `settings.json.corrupt-6a1d68dddb` is identical to the original,
live file valid again.

## D-6 / D-7 save handlers wrote anywhere
Cause: D-6, `dirPath` never checked; D-7, the sanitiser strips separators but leaves a bare `..`.
Change: one helper, `resolveTarget`, applied to the RESOLVED target (symlinks followed via the nearest
existing ancestor) at `file:save`, `file:saveFiles` (folder and each file name), `export:save`
(`exportSave.cjs` folder and each file name) and, for the same hole, `clip:save`. Rules: the target must
sit strictly inside `dirPath`, and `dirPath` must sit inside a folder the app knows: `clipper.saveDir`,
`saveDirs`, `clipsDir`, `dataDir` from settings plus any folder picked via `dialog:pickDirectory` this
session. `saveExportFiles` takes an optional `allowedRoots` (existing callers/test unaffected).
Real app, before: canary `.bashrc` `ino=902302 size=9` -> `size=5`, content `PWNED`; `esc.csv`
landed in the parent. After: both refused (`Unexpected save location`), canary unchanged (same
ino/size/sha), no `esc.csv`; controls (`folder:"ok"`, file inside chosen) still succeed.

## D-1 keeper file:startDrag unguarded
Cause: any renderer code could call it with no gesture in progress, wedging main. Reproduced: bare
`startDrag("/etc/hostname")` -> next IPC `NO ANSWER after 8s`. Change: (1) `preload.cjs` only forwards
`startDrag` within 1s of a genuine `isTrusted` `dragstart` (page script cannot forge trust or reach the
variable); (2) main requires the sender to be the main window and the path to be an existing regular
file inside the known folders (`dragTarget`). After: same call -> `ANSWERED true`.
**Not claimed:** the wider drag-freeze. This container has no window manager or real pointer, so a
real drag gesture reaching `startDrag` is untested here; a genuine drag may still wedge and needs
macOS/Windows verification. What is fixed is only the no-gesture path.
Note a behaviour change: dragging a file that is not inside a configured folder is now refused (logged).

## F-9 update check reporting "Up to date" without checking
Cause: `checkForUpdates()` resolves `null` when the check never ran; handler treated no version as
"none". Change: `interpretCheckResult` (`updateCheck.cjs`): null/no `updateInfo` -> `{ok:false}` plus an
`error` status ("The update check did not run..." with the releases link); only a real answer matching
the running version is `none`. Real app on Linux (GitHub unreachable): before `{"ok":true,"version":null}`
and a `none` event; after `{"ok":false,...}` and an `error` event. A true positive "Up to date" was not
exercised against a real feed (not provable here).
